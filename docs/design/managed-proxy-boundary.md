# 管理するプロキシの境界

[security.md](security.md#管理するプロキシの境界) の詳細。初回準備と管理設定は [中継手順](../managed-proxy.md) を参照する。

## 起動と経路

`proxy_mode`が`managed`のアカウントだけ、本文・画像の事前検証後または認証ロック取得後に中継を準備し、準備後に設定を再確認する。明示的な`start_proxy`でも起動できる。公開proxy URLは変えず、Cookie bindingを維持する。設定は資格情報ストア経由でだけ取得し、API引数・MCP応答にSSH鍵や接続先を含めない。読取り・設定一覧・保存Cookieの再利用は中継を起動せず、external呼出しは既存中継に干渉しない。

投稿・ログインの要求はTwitterAPI.ioへ送り、同サービスが公開プロキシへ接続する。公開口（中継サーバー）からloopbackポート、SSH逆転送、PCのloopback限定CONNECT出口を通り、住宅回線からXへ出る。出口はX/Twitter/Twimgのドメインの443番だけを許し、DNS全候補に特殊アドレスがあれば拒否する。検証済みIPへ直接接続して再解決を避け、接続数・容量・時間を制限する。無料Cloudflare Tunnel/Workersは代替として実装していない。

## 共有daemonとIPC

Windowsは設定別の名前付きパイプ、macOSは利用者専用ディレクトリ内のUnix socketへ接続し、未起動なら同じ実行ファイルを独立daemonとして起動する。Windowsでは親MCPの標準ハンドルを継承させない。macOSではディレクトリ・socketの所有UIDと権限、接続相手のUIDを照合する。IPCはv3の独立した名前空間で、旧JavaScript daemonとは接続しない。SSHと固定ポートの所有を一つに集約して複数チャットで共有する。IPC秘密はSSH鍵ファイルから導出し、設定識別子・双方のnonce・要求番号・操作・応答全体をHMACで結び付けて相互認証し、別設定への転送や過去応答の再利用を拒否する。

## 再接続と停止

SSHの再接続は経路だけを復旧し、投稿・ログインは再送しない。停止では最後に使った設定のsocket、timer、逆転送、ローカル出口を閉じ、生きている接続は転送解除と切断を有限時間だけ待つ。応答がない場合はVPS側のポート解放を保証しない。PCの消失はVPS側の生存確認（15秒間隔・無応答3回）で検知する。MCP終了ではそのクライアントだけが離脱し、全クライアントの離脱から5分後にdaemonを終了する。ポート競合では別設定の所有者を終了させず固定コードで拒否する。停止と並行する別プロセスの起動要求は、まだdaemonへ接続していなければ停止後に完了することがある。

## 中継の診断記録

拒否が増えた時期の経路変化を後から切り分けるため、`src/relay_log.rs`が`<状態ルート>/relay/events.jsonl`へ状態の移り変わり（`daemon_started`・`daemon_stopped`・`starting`・`ready`・`reconnecting`・`failed`・`stopped`）を固定コードと時刻だけで常に記録する。`daemon_stopped`の理由は`idle`・`shutdown`・固定のエラーコードで、設定は`config`のSHA-256先頭12桁で見分ける。ホスト・ポート・鍵・ユーザー名・IP・生エラー文は残さない（出口IPは外部への問い合わせが要り、ローカルのアドレスは個人の情報のため）。14日・500件・128KiBを超えたら古い順に消し、本人限定・リンク拒否とする。途中で残った`relay\`直下の`.relay-*.tmp`（通常ファイルだけ）は片付ける。書込みは1つの書き手タスクが1件1秒で打ち切り、失敗は無視して中継を止めない。閲覧はCLIの`--relay-log show`だけで、IPCの契約は変えていない。
