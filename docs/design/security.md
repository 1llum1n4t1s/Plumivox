# 秘密・通信・プロキシの境界

[DESIGN.md](../../DESIGN.md) の不変条件のうち、秘密・保存・通信と管理するプロキシの詳細。外部経路の初回準備と管理設定は [中継手順](../managed-proxy.md) を参照する。

## 不変条件

- **秘密の境界**：資格情報と復号Cookieは内部処理で使用する。公開状態は準備状況であり、Xでの認証成功を保証しない。WindowsはDPAPIのCurrentUserとユーザー限定ACL、macOSはログイン利用者のKeychainと本人限定のファイル権限を使う。認証処理はOSのネイティブAPIを使い、PowerShellに依存しない。
- **保存の結び付け**：保存先はアカウント名と小文字ユーザー名のハッシュで分け、schema version 2、ユーザー名、APIキーとプロキシのbindingを照合する。保存先はリンク先も検査し、リポジトリとCodex・Claude Codeなどのユーザー設定ディレクトリ（`~/.codex`・`~/.claude`、`CODEX_HOME`・`CLAUDE_CONFIG_DIR`の移動先）を拒否する。旧保存形式は読取り互換であり、更新先にはしない。
- **通信の境界**：API接続先は `https://api.twitterapi.io` と検証用HTTPループバックに限定し、リダイレクトを拒否する。応答はストリームで読み、10MiBを超えたら受信を中止する。タイムアウトとMCPの中止シグナルをHTTPへ渡し、画像アップロード後も中止状態を確認して投稿開始を防ぐ。提供元の生エラーは外へ返さない。唯一の例外は[拒否文面の記録](rejection-log.md)で、既定で無効・期限付き・伏字処理・本人限定のローカルファイル・MCPの応答とMCPサーバー（stdio）の標準出力・標準エラーへ出さない、の5点を満たすときだけ許す。閲覧はCLIの`show`が標準出力へ出すだけとする。

## 拒否文面の記録

`plumivox --rejection-log on [--days N]`で期限付きに有効化し、伏字処理した`post_tweet`の拒否文面だけを本人限定のローカルファイルへ残す。対象・伏字・保存先・上限は[拒否文面の記録](rejection-log.md)を参照する。

## 投稿の冷却ガード

同じXアカウントへ別々のセッションから短い間隔で投稿するとXに自動化を疑われて拒否され、拒否直後の再送はさらに悪化させる。`src/post_guard.rs`は、Xのユーザー名ごとに全プロセス共通の冷却をかけ、冷却中の`post_tweet`はXへ何も送らず（提供元の課金も起こさず）`POST_COOLDOWN`で断る。値は固定の定数で、設定項目は無い。

- **順序**：`get_account`→`prepare_post`（検証）→`acquire`→`ensure_proxy`→`send_recorded`→`finish`。`ensure_proxy`が失敗したときは結果を記録せず`release`で放す。
- **保存**：`<状態ルート>/post-guard/<hash>.json`と同じフォルダーの`<hash>.lock`（ファイルロック）。`hash`は`post-guard\n`＋小文字のユーザー名（設定名ではなくXのユーザー名）のSHA-256。フォルダー・ファイルは本人限定、リンクは拒否し、状態は64KiBまで。一時ファイル（`.post-guard-<hash>-<乱数>.tmp`）へ書いてから置換し、書込みの途中で止まって残った自分の分（名前に同じ`hash`を含む通常ファイルだけ）はロックを取った後に片付ける。排他は約500ms待ち、取れなければ別の投稿の送信中として`post_in_progress`（1分）で断る。
- **状態に入れるもの**：schema、設定名（Xのユーザー名と一致するとき、または設定名がユーザー名を含むだけのときも`<user>`。4文字未満のユーザー名は完全一致のときだけ。`<user>`で残った状態は`clear --account 設定名`では選べない）、更新時刻、最後の試行時刻、送信中印（`inFlight`）、冷却（理由・開始・期限）、strikesと最後のstrike時刻、履歴（最大32件。時刻・段階・エラーコード・分類・`xErrorCode`・`xHttpStatus`）。履歴には小文字と`_`だけの短い固定語しか残さない。**入れないもの**：本文、提供元の文面、ユーザー名（ファイル名のハッシュを除く）、資格情報。
- **規則**（時間は分）：

  | 結果 | 冷却の理由 | 長さ |
  | --- | --- | --- |
  | 成功・投稿作成まで進んだ失敗（投稿作成段階の`proxy`を含む拒否も、`postAttempted`が真なら含む） | `min_interval` | 5（成功ではstrikesを0に戻す。strikeは数えない） |
  | `POST_UNCERTAIN`・`post_id_missing` | `previous_uncertain` | 15 |
  | 前回が`finish`なしで終わった（`inFlight`が残る） | `interrupted` | 15 |
  | 状態が読めない・形式不正・schemaが0などこの版で解釈できない形・上限超過で作り直した | `guard_state_reset` | 15 |
  | この版より新しいschemaの状態 | `guard_state_reset` | 15（作り直さず、ファイルを書き換えずに拒否だけ返す） |
  | Xの拒否だが分類できない（`xRejected`） | `unclassified_rejection` | 15 |
  | `rate_limit`でXの拒否と分かる（`xRejected`が真。Xのコード88、`x_status`の429など） | `rate_limit` | 15×2^(strikes-1) |
  | `rate_limit`で`xRejected`が無い（提供元のHTTP 429など） | `rate_limit` | 15（固定。strikeを数えない） |
  | `automation_suspected` | `automation_suspected` | 180×2^(strikes-1) |
  | `daily_limit` | `daily_limit` | 360×2^(strikes-1) |
  | `account_locked`・`account_suspended` | `account_locked` | 1440×2^(strikes-1) |

  複数に当たれば最長を採り、既存の冷却は新しい期限が前なら残す。上限は24時間。strikesはstrikeを数える拒否ごとに1増え（上限64。`xRejected`の無い`rate_limit`は数えない）、成功、または最後のstrikeから48時間で0に戻る。提供元だけで止まった拒否（HTTP 401・402、または分類が`api_key`・`credits`・`proxy`だけでXの拒否の印が無い）は、Xまで届いていないので冷却をかけない。ただし投稿作成の段階（`postAttempted`が真）の`proxy`を含む拒否は、中継がXへ送った後に切れた可能性があるので`min_interval`（5分、strikeなし）をかける。画像アップロード段階の`proxy`拒否、`api_key`・`credits`だけの拒否、HTTP 401・402は冷却なしのまま。投稿前の失敗・取消も記録しない。
- **時計**：保存した時刻が今より120秒以上未来なら時計が戻ったとみなし、冷却は開始を今、期限を今＋元の長さ（上限24時間）へ置き直し、最後の試行が未来なら今から最小間隔の冷却をかける。
- **止める条件（fail-closed）**：状態ルートが無い、フォルダー・ロック・状態がリンクや通常ファイル以外・読めない、ユーザー名が空、送信前の書込みに失敗したときは、送らず`POST_GUARD_UNAVAILABLE`で止める。冷却中の書込み失敗は拒否が変わらないので無視する。
- **解除**：MCPからは解除できず、ツールも作らない。利用者本人がCLI（`plumivox --post-guard status`、`clear [--account 設定名 | --user Xユーザー名]`）で確認・解除する。状態の`account`が`<user>`になったものは`--account 設定名`では選べず、`--account`で0件のときは`--user`を使う案内を1行表示する（終了コード0）。`clear`は端末での確認入力（対象名、すべては`all`）が必須で、冷却・strikes・`inFlight`を消し（履歴と最後の試行は残す）、送信中でロックが取れない状態は解除しない。終了コードは成功0、保存先の異常・送信中1、引数の誤り・端末でない・確認の不一致2。
- **限界**：シェルを使えるエージェントはCLIや状態ファイルの削除で解除できてしまうため、強い防御ではない。想定は、Xへ短い間隔で送って自動化と疑われる事故を、誤って重ねないことである。AIが読む文言（`nextStep`・ツール説明）にCLIのコマンド名は書かず、本人へ伝えるよう促すだけにする。
- **採用した設計判断**：共有daemonに置かないのは、daemonがmanagedの設定ごとにしかなく5分で終了して状態が消えるため。ファイル＋ロックなら全プロセス・非managedでも共通にできる。冷却中に待って後から送らないのは、自動再送と同じになり、成否不明の投稿を重ねるため。待つ時間は`retryAfter`として返し、再開は呼出し側（本人）に委ねる。ただし`min_interval`・`post_in_progress`はXの拒否ではなく通常の間隔の確保なので、`POST_COOLDOWN`の`nextStep`は`retryAfter`の後に同じ内容で1回だけ呼んでよいと伝える（それ以外の理由は本人に伝えて待つ）。

## 管理するプロキシの境界

`proxy_mode` が `managed` のアカウントだけ、本文・画像の事前検証後または認証ロック取得後に中継を準備し、準備後に設定を再確認する。明示的な `start_proxy` でも起動できる。公開proxy URLは変更せず、Cookie bindingを維持する。設定の取得は資格情報ストア経由に限定し、API引数・MCP応答にSSH鍵や接続先を含めない。読取り・設定一覧・保存Cookieの再利用は中継を起動せず、external呼出しは既存中継に干渉しない。

投稿・ログインのAPI要求は従来どおりTwitterAPI.ioへ送り、同サービスが公開プロキシへ接続する。公開口から中継サーバーのloopbackポート、SSH逆転送、PCのloopback限定CONNECT出口を通り、住宅回線からXへ接続する。出口はX/Twitter/Twimgのドメインと443番だけを許可し、DNS全候補に特殊アドレスがあれば拒否する。検証済み公開IPへ直接接続してDNSの再解決を避け、接続数・容量・時間を制限する。

Windowsは設定別の名前付きパイプ、macOSは利用者専用ディレクトリ内のUnix socketへ接続し、未起動なら同じネイティブ実行ファイルを独立daemonとして起動する。Windowsでは起動時に親MCPの標準ハンドルの継承を抑止し、daemonが終了済みMCPの通信パイプを保持しないようにする。macOSではディレクトリ・socketの所有UIDと権限、接続相手のUIDを照合する。ネイティブIPCはv3の独立した名前空間を使い、旧JavaScript daemonと接続しない。SSHと固定ポートの所有を一つに集約して複数チャットで共有する。IPC秘密はSSH鍵ファイルから導出し、設定識別子・クライアントとチャネルのnonce・要求番号・操作・応答内容全体をHMACで結び付けて相互認証する。同じ鍵を使う別設定への転送や過去応答の再利用を拒否する。

SSHの再接続は通信経路だけを復旧し、投稿・ログインは再送しない。停止では最後に利用した設定の共有daemonのsocket、timer、逆転送、ローカル出口を閉じる。生きている自己SSH接続は転送解除応答と切断完了を有限時間だけ待ち、次の起動との競合を抑える。応答がない場合や既に通信が切れている場合は、VPS側のポート解放を保証しない。PCが消失した接続はVPS専用ユーザーの生存確認（15秒間隔・応答なし3回）で検知する。MCP終了ではそのクライアントだけを離脱し、他チャットの中継を維持する。全クライアントが離脱して5分後にdaemonを終了する。ポート競合では別設定の所有者を終了させず固定コードで拒否する。

別のMCPプロセスで停止と並行して進んでいる起動要求は、まだ共有daemonへ接続していない場合、停止後に完了することがある。

**中継の診断記録**：投稿の拒否が増えた時期に経路が変わったかを後から切り分けるため、`src/relay_log.rs`が`<状態ルート>/relay/events.jsonl`へ、daemonと中継の状態の移り変わり（`daemon_started`・`daemon_stopped`・`starting`・`ready`・`reconnecting`・`failed`・`stopped`）を固定コードと時刻だけで常に記録する（有効化の操作は無い）。`daemon_stopped`の理由は`idle`・`shutdown`・固定のエラーコードで、設定は`config`のSHA-256先頭12桁で見分ける。ホスト・ポート・鍵・ユーザー名・IP、提供元やSSHの生エラー文は残さない。公開IP（出口IP）を残さないのは、外部へ問い合わせないと公開IPは取れず、ローカルのアドレスは個人の情報になるため。古さ14日・500件・128KiBを超えたら古い順に消し、フォルダー・ファイルは本人限定でリンクを拒否する。書込みの途中で止まって残った一時ファイル（`relay\`直下の`.relay-*.tmp`のうちリンクでない通常ファイル）は片付ける。書込みは1つの書き手タスクが1件ずつ行い、1件を1秒で打ち切り、失敗は無視して中継を止めない・遅らせない。閲覧はCLIの`--relay-log show`だけで、MCPツールは無い。IPCの契約は変えていない。

公開口は引き続き中継サーバーが担当し、無料Cloudflare Tunnel/WorkersをHTTP CONNECT公開プロキシの代替として実装していない。
