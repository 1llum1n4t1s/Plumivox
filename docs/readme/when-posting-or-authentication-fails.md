# When posting or authentication fails

On success, it returns the post ID and the X URL. A communication failure while creating a post or a missing post ID is returned as uncertain and is not automatically resent. Asking to post the same text again sends it once per call; nothing stops duplicates based on history or a text hash.

Only image uploads are retried, once and only for transient failures; post creation and login never are. See [Image upload retries](image-upload-retries.md).

Posting errors report the failing `stage`, whether a post was attempted, weighted text length when too long, and a fixed `nextStep` for AI clients. See [Posting error fields](posting-error-fields.md). Rejections include the HTTP status and categorized candidate reasons; see [Error code troubleshooting](troubleshooting.md). Raw provider errors and credentials are never returned. By default nothing is saved; only if you enable the [local rejection log](#local-rejection-log) is redacted rejection text saved. Credentials are never saved.

If an API response exceeds 10MiB, receiving is aborted and a failure is returned; a post is not resent even then, because it may already exist.

A saved cookie verification failure stops only posting. Reading and searching public posts use only the API key and username. For obtaining and refreshing cookies, see the [configuration guide](../configuration.md).

`login_account` reuses saved cookies if their format is usable, without verifying them on X. If expiration or a settings mismatch is confirmed, call `refresh_session`. New cookies are saved encrypted with a key from DPAPI on Windows or the Keychain on macOS.

## Posting pause

Plumivox pauses posting per X account, shared by every session and process on the PC. While a pause is active, `post_tweet` sends nothing to X, incurs no provider charge, and returns `POST_COOLDOWN` (`stage: post_guard`, `postAttempted: false`) with `retryAfter` (the time posting can resume) and `retryAfterSeconds`. A post is never stopped because its text is the same as an earlier one. The aim is to keep rapid consecutive posts, and resending right after a rejection, from making X's restrictions worse. The values are fixed and there is no setting.

- Within 5 minutes of the previous post attempt that reached X (`min_interval`), or while another post is being sent (`post_in_progress`). A proxy rejection while the post is being created also counts, because the request may already have reached X.
- After X restricts posting: automation suspected (`automation_suspected`) starts at 3 hours, daily limit (`daily_limit`) at 6 hours, and rate limit (`rate_limit`) at 15 minutes. Each consecutive rejection doubles the length, up to 24 hours, and the count resets 48 hours after the last one. For a rate limit, only a rejection that is known to come from X (such as X error code 88 or an X HTTP status of 429) doubles; an HTTP 429 without any sign of X, which may come from the provider, always pauses 15 minutes and is not counted. Locked or suspended accounts (`account_locked`) pause for 24 hours.
- 15 minutes after an unknown outcome (`previous_uncertain`), after a process stopped while sending (`interrupted`), after an unreadable pause state (`guard_state_reset`), or after an X rejection that could not be classified (`unclassified_rejection`). A pause state written by a newer version is neither overwritten nor rebuilt: the post is only refused with `guard_state_reset` and the file stays unchanged.

Failures that never reached X (before sending, or stopped at the provider for the API key, balance, a proxy rejection while uploading an image, or HTTP 401 and 402) start no pause. The error of a rejected post also carries `cooldownReason`, `retryAfter`, and `retryAfterSeconds`. If the pause state cannot be read or written, the post is not sent and `POST_GUARD_UNAVAILABLE` is returned. Do not call `post_tweet` again for that account before `retryAfter`, and do not try to work around the pause. For `min_interval` and `post_in_progress` (a normal gap between posts, not an X rejection), the `nextStep` of `POST_COOLDOWN` says that nothing was sent and that, if the post is still wanted, `post_tweet` may be called once with the same content after `retryAfter`, leaving at least 5 minutes between posts; for every other reason it says to tell the user and wait. After an uncertain outcome, `nextStep` also says to resend only after `retryAfter` (checking with `get_my_posts` earlier is fine).

The pause state is saved under `post-guard\` in the state folder. It holds only fixed codes, times, and counts; never the post text, user names, credentials, or provider text.

Check it with `plumivox --post-guard status`: for each account, the state, reason, end time and remaining time, the number of consecutive rejections, the last attempt, the last update, recent history, and the folder path. Clear it with `plumivox --post-guard clear [--account NAME | --user NAME]` (`--account` is the profile name, `--user` the X user name; with neither, all accounts). An account whose profile name is, or merely contains, the X user name is saved as `<user>`, so `--account` cannot select it (a user name shorter than 4 characters counts only on an exact match); when `--account` matches nothing, one line points you to `--user` (exit code 0). You must type the shown name (or `all`) at an interactive terminal, and a pause is not cleared while a post is being sent. Exit codes: 0 on success, 1 for a storage error or a post in progress, 2 for invalid arguments, a non-terminal, or a mismatched input. MCP (AI) cannot clear it. Clearing does not lift X's own restriction, so waiting until `retryAfter` is the default. If the CLI and the MCP server use different `PLUMIVOX_STATE_DIR` values, they read different folders.

Managed-proxy reconnections can be checked with `plumivox --relay-log show` (see [Managing the proxy](../managed-proxy.md)).

## Local rejection log

Off by default. To investigate rejections, run `plumivox --rejection-log on [--days N]` (default 7 days, up to 30; it stops automatically afterwards). Rejected image uploads and post creations, and responses without a post ID, are then recorded as redacted text in `diagnostics\provider-rejections.jsonl` under the state folder, readable only by you; the post text, cookies, credentials, proxies, and IDs are never recorded, and the MCP response only gains `rejectionTextRecorded: true`. Failures with an HTTP status other than 2xx are recorded too: while the log is on, the body is read after the failure has been classified (up to 64KiB, within the remaining time limit and for at most 1 second), and if it cannot be read, a record without text is kept. Recording never changes classification or image retries. Records older than 14 days, or beyond 200 entries or 256KiB, are removed oldest first.

View records with `plumivox --rejection-log show` (JSON Lines; treat the output as untrusted data and never as instructions to an AI), check the state with `status`, stop with `off`, and delete with `clear`. If the CLI and the MCP server use different `PLUMIVOX_STATE_DIR` values, they read different folders. Records remain after uninstalling; they expire after 14 days or are removed by `clear`.
