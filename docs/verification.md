# 検証方針

実装前に想定する失敗を以下に定義する。利用者経路はMCPクライアントから独立したネイティブサーバープロセスを呼び出すE2Eで検証する。署名・文字数・OSの保存・SSH・IPCなどの境界はRustテストでも確認し、両方の結果を区別する。

macOSの対話セットアップE2EはRustから`libc::openpty`で制御TTYを作り、入力時のECHO無効化を確認する。PythonやNode.jsは使わない。

Windowsの`cargo xtask build`はSigiluneで署名し、本人の発行者・信頼チェーン・タイムスタンプの検証後に配布物を置換する。Sigilune不在・認証・署名・検証の各失敗ではビルドを失敗させ、既存配布物を保持する。`SIGILUNE_EXE`に存在しないパスと失敗終了するfixtureを指定し、実際の`cargo xtask build`が非ゼロ終了し既存配布物のハッシュが不変であることを確認する。通常の`cargo xtask build`で署名済み配布物を生成して`sigilune verify --signer "Open Source Developer Yuichiro Shinozaki"`、Defender個別スキャン、MCP起動で確認する。`build-unsigned`と`ci-distribution-build`単体はWindowsの署名を省く準備物を生成し、配布CIでは後続の署名・`ci-windows-verify-signature`の成功をもって署名済みとする。

手動起動の配布CIはWindowsとmacOSそれぞれで`cargo xtask check`・`cargo xtask test-e2e`を実行し、fixture機能を含まないWindows x64／macOS ARM64の準備用成果物を最後に再ビルドしてR2へ保存する。WindowsのCI成果物は、Environment `release`の承認後にSigiluneで署名し、`cargo xtask ci-windows-verify-signature`で本人の署名・タイムスタンプを確認してから保存する。macOSでは同じジョブ内で専用Keychainを作成・unlockして`PLUMIVOX_TEST_KEYCHAIN`へ渡し、既定Keychain・検索一覧を変更せず、終了時に専用Keychainを削除する。CIの起動・実R2通信は別途実行結果が必要で、ローカルの構文・Rustテストの成功を代用しない。手順は [配布成果物](distribution.md) を参照する。

| R2成果物の失敗条件 | 期待する結果 |
| --- | --- |
| identity・target・設定・引数が不正 | 保存・取得を拒否し、資格情報を表示しない |
| 同じidentityのオブジェクトが存在する | 条件付きPUTで上書きを拒否する |
| 保存が途中で失敗しmanifestがない | 完成済み成果物として取得できない |
| manifestのidentity・ファイル名・サイズ・SHA256が不一致 | 検証に失敗し、取得済みとして扱わない |
| 出力先が既存ディレクトリ | 上書きせず拒否する |

`cargo test --locked --package xtask`でR2の入力・manifest・ハッシュ検証を確認する。実R2の認証・条件付き保存・取得、GitHub-hosted macOSのKeychainとCI全体は、実環境で実行するまで未検証として扱う。

PCセットアップはWindows・macOSともネイティブの`--setup`を対象OSで呼び出して検証する。VPSはRustインストーラーとBash互換CLIを区別して検証する。想定する失敗は次のとおり。

| セットアップの失敗条件 | 期待する結果 |
| --- | --- |
| 別のWindows・macOS利用者が初回起動する | そのOSと利用者の保存先を選び、特定利用者の絶対パスを参照しない |
| 選択済み設定が不正・消失 | 別ファイルへ切り替えず設定エラー |
| 既存鍵・既存プロファイル・中継設定がある | 上書きを拒否し、既存情報を保持 |
| 保存先がリンク・リポジトリ・Codex内、所有者やACL／Unix権限が不適切 | 保存前に拒否し、秘密値を公開しない |
| ホスト指紋・ポート・2FA秘密鍵・秘密鍵が不正 | ローカルで拒否し、API・SSH通信を行わない |
| 書込み準備中に設定が変更された | 検出した変更を上書きしない |
| VPS CLIが不正引数・パスワード引数を受け取る | 変更コマンドを呼び出さず拒否 |
| root権限・対応OS・UFW・SSHの準備が不足 | 原因を示して停止し、既存設定を変更しない |
| VPSのSquid・専用利用者・ポートが競合する | 既存サービスを停止・上書きしない |
| Rust版・Bash版VPSの新規導入でACL・拡張属性・SELinux・必要なcapabilityを安全に扱えない | 変更前に拒否する。既存の同一導入の読取り確認とは区別する |
| Rust版・Bash版VPSの新規導入で同一ファイルシステム内のRENAME_EXCHANGEが利用できない | 安全に停止する。書込みprobeを行わない--checkの合格を交換機能の検証成功と扱わない |
| Bash版の新規導入でGNU mvが--exchange/--no-copy、lnが-Tに未対応、またはgetfacl・getfattr・sync・readlink・lsattrがない | 変更前に停止し、管理者が環境を確認するまで必要なコマンドやcoreutilsを自動導入・更新しない |
| 新規導入が初期user namespaceでない、CAP_SYS_ADMINがない、SSH設定と親のmount IDが異なる・確認不能、保持不能なinode flagsがある | 新規導入を変更前に拒否する。既存の同一導入の読取り確認とは区別する |
| 新規保存先に同名のファイル・ディレクトリが存在する | 上書き・再利用・既存対象の権限変更で回避せず、競合を拒否する |
| 一時データの清掃が失敗する | stage・バックアップの保持先を通知し、管理者が今回分と交換状態を確認できるようにする |
| SSH設定を交換した旧ファイルを別処理が開いている | root限定バックアップディレクトリを保持する。旧FDの利用終了、新旧内容とSSH動作の確認前に自動清掃しない |

`tests/setup_e2e.rs`は専用鍵の生成とACL、設定の保存・保持・拒否、保存先の選択、ローカル確認を検証する。Rust版VPSインストーラーは`cargo test --locked --package plumivox-vps-installer`でCLI・変更拒否経路を検証する。Linux固有のファイル交換・属性境界はLinux上で確認し、他OSのCLI検証とは区別する。`tests/setup_vps_e2e.rs`はBash互換経路の構文、実CLIのヘルプ・不正入力・権限拒否と変更コマンド未呼出しを検証する。WindowsのGit Bash検証では、Linuxでのパッケージ導入・Squid起動・SSH認証の成功は未検証である。実VPSへの接続・ログイン・投稿はこのE2Eでは行わない。実システムへの導入は未確認であり、CLIやfixtureの成功をその代用にしない。

| 失敗条件 | 期待する結果 |
| --- | --- |
| 複数の投稿先があり有効な既定がなくaccountが省略された | アカウント指定を要求し、通信しない |
| 64文字を超える設定済みアカウント名 | 一覧に表示した名前をそのまま指定して読取りできる |
| APIキーがない、Cookieがない、保存Cookieの照合が不一致 | 秘密を表示せず設定エラー。読み込みにはCookieを要求しない |
| 空の投稿、280の加重文字数を超える投稿 | アップロード・投稿前に拒否 |
| URL、日本語、複合絵文字が含まれる投稿 | twitter-textの加重文字数とUnicode 17の複合絵文字の重み2で判定。280は送信し282は通信前に拒否 |
| 画像の形式不正、サイズ超過、相対パス、5枚以上 | 送信前に拒否 |
| 4画像のアップロード、途中の画像で失敗 | 事前検証した画像の順序・内容を維持し、途中失敗では投稿を送信しない |

| 画像アップロードの再度の502・503・504、401・429・500、JSON拒否・不正応答・タイムアウト・通信不明 | 再度の一時HTTP失敗は2要求で打ち切り、他の失敗は1要求で停止。投稿は送信しない |
| 通常要求の時間枠を超える画像アップロード | 画像専用の時間枠内なら完了を待ち、成功後に投稿を1回だけ送信する。通常45秒、画像は1枚120秒が既定 |

| 画像のタイムアウト・通信切断 | API_UNAVAILABLEを維持し、failureKindのtimeout／networkで区別する。生エラーを返さず、再送・投稿をしない |
| uploadのHTTPエラー本文がストリームで続く | 生本文を読まず受信をcancelし、接続資源を解放してから次の処理へ進む |
| 画像拒否・投稿拒否・投稿応答のID欠落 | 既存のエラーコードに安全なstage・postAttempted・uploadAttemptsを追加し、失敗段階と投稿要求の有無を区別する |
| Cookie不足・中継準備後の設定再確認失敗 | 既存のcode・messageを維持し、pre_send・postAttempted:false・uploadAttempts:0を返す。APIを呼ばず、未知の内部エラーへ未送信の断定を加えない。他ツールのエラー形式も広げない |
| APIの401/429/5xx、非JSON、HTTP 200内のerror | 秘密や提供元の生エラーを返さず失敗として返す |
| APIの拒否JSONが認証・プロキシ・残高・未知の理由や秘密値を含む | `httpStatus`・固定分類 `rejectionReasons`・分類元 `rejectionReasonSource` だけを追加し、任意コード・request ID・秘密値を応答と診断へ出さない。読取り・ログイン・画像・投稿で確認し、要求回数とstage・成否不明の契約を保つ |
| 拒否メッセージが非文字列・4096 UTF-8バイト超、`errors`が多数、診断用でないフィールドに理由がある | 指定フィールドと先頭8件のerrorsだけを上限付きで分類し、未認識はunknownとする。生応答全体や任意フィールドを診断へ転載しない |
| 10MiBを超えるAPI応答、UTF-8文字途中の通信分割 | 上限超過で受信を打ち切る。上限内の分割文字は正しく復号する。投稿の超過応答は成否未確定として再送しない |
| 投稿成功に見えるが投稿IDがない、通信の成否が不明 | 成功扱いせず、自動再送しない |
| 同じ投稿を明示的に二度呼び出す | 各呼び出しで一回ずつ送信する。ローカル履歴で停止しない |
| フォロー先が空、保護アカウントを含む、一覧が複数ページ | 公開投稿の取得範囲・未取得範囲を明示 |

| 暗号化保存ファイルが2MiB境界に達する、破損・別利用者の暗号文である | 上限とOS別の復号境界で検証し、読めない保存セッションを無効として扱う |
| macOSのKeychainが利用不可、暗号化ファイルのタグやnonceが不正 | 平文保存や別Cookieへの切替を行わず安全に失敗。読取り4ツールはKeychainを呼び出さない |

| ログイン成功応答のCookieが保存に使えない形式 | LOGIN_FAILEDとして返し、保存済みセッションを維持 |
| 保存本体の置換を指示した後に成功応答を確認できない | AUTH_SAVE_UNCERTAINとして更新済みの可能性を伝え、未変更と断定しない |
| 同じアカウントへ同時にログインを要求 | 複数MCPプロセスでもAPI呼出前から保存完了まで排他し、競合をAUTH_BUSYとして拒否 |
| ロックを保持するMCPプロセスが終了 | ロックを解除し、次の認証更新を妨げない |
| 認証ロックの所有が失われる | 旧処理から保存しない。別MCPの新しいセッションを上書きしない。Windowsの所有スレッドとmacOSのファイルロックをそれぞれ確認 |
| 投稿拒否後にセッションだけを更新 | 更新は行うが、失敗した投稿を自動再送しない |
| ログイン応答・標準エラー・証拠ファイル | APIキー・Cookie・パスワード・2FA秘密鍵・プロキシ資格情報を含めない |
| vava／blblの投稿手順が旧スクリプトを参照 | 全呼び出し元をPlumivoxのMCPツールへ統一し、旧専用ファイルの撤去を確認 |

E2Eでは外部サービスの代わりにlocalhostのHTTPサーバーを使い、HTTPメソッド・認証ヘッダー・本文・要求回数を記録する。検証結果は利用者の一時ディレクトリにある作業別フォルダーへ書き、終了後に必要な証拠だけ保持する。接続先の差し替えと失敗注入は`test-fixture`ビルドに限定し、配布実行ファイルへ環境変数などの迂回経路を設けない。実際のXへの投稿はこの検証に含めない。

## 既定アカウントの失敗条件

- 複数登録・既定なしの省略呼出しはACCOUNT_REQUIREDとして通信前に拒否する。
- 登録済みのdefault_accountがあれば、検索・読取り・投稿・認証は省略時にその設定名を使う。明示accountと既存の環境変数による選択を優先する。
- 空文字・null・文字列以外・未登録名のdefault_accountは、省略時にACCOUNT_DEFAULT_INVALIDとして通信前に拒否し、先頭や唯一の登録先へ戻らない。明示accountなら指定先を使える。
- list_accountsはdefault_accountをアカウントとして列挙せず、有効な省略先だけにisDefaultを返す。選択不能でも一覧は確認できる。
- 設定を更新・再起動しても既定を読み込み、別accountを明示した投稿を既定へ送らない。既定が変わっても既に開始した認証・中継準備の送信先を変更しない。
- セットアップは初回登録を既定として保存し、既存の有効既定は保持する。既定だけの変更でも未登録名・保存競合・読込み失敗を拒否し、アカウント資格情報や中継設定を変更しない。

| 失敗条件 | 期待する結果 |

| ヘッダー・DNS・接続が15秒以内に完了しない、60秒の無通信、10分の最大寿命 | 接続とタイマーを終了し、DNS待機の継続による接続開始を防ぐ |
| クライアント中断、上流障害、出口停止、停止と起動の競合 | 全ソケットを閉じ、未完了DNSの結果から接続を開始しない。停止完了時に接続数0 |
| 別プロセスが出口ポートを使用中 | PROXY_PORT_BUSYで安全に失敗し、既存プロセスを停止しない |
| 応答・状態・標準出力に内部エラーや設定・宛先・IPが混ざる | 固定エラーとrunning・activeConnectionsだけを公開し、標準出力にログを出さない |

## 管理プロキシの別プロセスE2E

実装前に固定する失敗条件は、SSHホスト鍵不一致・公開鍵認証失敗・ローカルポート競合・起動中の取消・接続切断後の再接続・明示停止後の復活・停止中の通信残存・externalアカウントの投稿による共有中継の停止です。いずれもAPI投稿の自動再送や秘密値の出力を起こしてはいけません。CONNECTでは禁止ドメイン・private IP・公開IPとprivate IPが混ざったDNS応答を外向き接続前に拒否し、検証済み公開IPを接続関数へ渡すことも確認します。

SSH停止では、転送解除の応答まで旧リスナーの解放を遅らせ、`stop_proxy` 直後の `start_proxy` で同じポートを確保できることを確認します。転送解除に応答しないSSHも有限時間で切断し、認証中の取消・認証失敗で停止を待ち続けないことを確認します。別所有者がremoteポートを使用する場合は `PROXY_REMOTE_BIND_FAILED` の恒久失敗にし、そのリスナーを維持して自動再試行やAPI再送をしません。

同時に起動を待つ複数の要求は、それぞれ一度だけ完了させます。一つの待機を取り消しても他の待機を妨げず、停止・認証失敗では残る待機すべてに対応する結果を返します。分割したCONNECTヘッダーと同梱した先行データも、単一受信と同じ順序で転送します。

管理・共有のどちらも、秘密鍵の空ファイル・非通常ファイル・読取り不能・1MiB超をSSH/API開始前に拒否します。共通の読取り処理では読取り上限、作業Bufferの消去、ファイル解放を保ち、共有IPCは従来のドメイン文字列付きハッシュを使用します。共有側だけのホスト名小文字化・鍵パス正規化と、管理側の表記維持・null許容を変えないことも比較します。

`cargo test --locked --lib`はRustのCONNECT出口・DNS検証・SSH転送・ホスト鍵照合・IPC認証の境界を確認します。通信・DNSの差し替えはテスト内だけに置き、配布実行ファイルの環境変数へ検証用の迂回経路を設けません。実際のXや実際のSSHホストへ通信しません。

## 共有プロキシdaemonの失敗条件

| 失敗条件 | 期待する結果 |
| --- | --- |
| 同じ設定で二つのMCPプロセスが同時に起動 | 一つのdaemonだけがSSHと固定ポートを所有し、両MCPからreadyを確認できる |
| 一方のMCP終了・起動待機の取消・external投稿 | 他方の中継とCONNECT通信を維持し、API投稿を再送しない |
| 一方から明示的にstop_proxy | 全利用者の中継を停止し、daemonの自動再接続で復活しない |
| 利用中のMCPが存在、または全利用者が離脱 | 利用中はidle終了せず、全離脱後に指定の待機時間でSSH・IPC・出口を閉じる |
| IPCの認証不一致、認証前コマンド、巨大frame | 認証済み状態を変更せず接続を拒否し、共有秘密・SSH鍵・設定を標準出力や証拠へ出さない |
| macOSのUnix socketの親・socket・接続相手が別UID、または共有権限やリンクがある | 所有者と権限の境界で拒否し、他利用者のdaemonへ接続・操作しない |
| IPC frameを分割・一括・分割の順に受信 | 正規の認証と要求番号を照合し、受信の分割方法にかかわらず同じ応答を返す |
| 過去challenge・resultの再利用、署名後のstatus改変、同じ秘密鍵を使う別設定scopeのMAC | client/server双方のnonce・channel・requestId・全応答内容・設定contextを照合して拒否。正規の署名済み応答は受理 |

`cargo xtask test-proxy-e2e`と`cargo xtask test-proxy-shared-e2e`は、検証用バイナリのビルドとプロキシのRustテストに続いて、同じプロキシE2Eを実行します。二つの別プロセスのMCP、独立したdaemon、Rustの偽SSH・HTTPサーバーで共有ライフサイクルを確認します。DNS・TCPの製品実装は置き換えません。出力先は`PLUMIVOX_PROXY_NATIVE_E2E_OUTPUT_DIR`またはユーザーの一時ディレクトリ配下`Codex/Plumivox/<UUID>`で、`summary.json`と`ssh-trace.json`を読みます。偽鍵・設定の清掃は呼び出し側が担当します。

## ビルドと実行

VPSの正式成果物は`cargo xtask build-vps x86_64`・`cargo xtask build-vps aarch64`で生成する静的ネイティブ実行ファイルです。配布CIでは対応するLinux CPUで実行ファイルの起動を確認し、Windows・macOS本体とともに既存R2経路へ保存します。CI処理はRustに集約します。ローカルの検査成功は実R2通信・CI起動の成功とは別で、実R2/CIは未確認です。設定と取得手順は[配布手順](distribution.md)を参照してください。

開発時だけリポジトリをクローンします。プラグインのインストール元にはこの作業ディレクトリを登録せず、[GitHubの最新mainを参照する手順](../README.md#インストール)を使います。

```powershell
git clone https://github.com/1llum1n4t1s/Plumivox.git
cd Plumivox
cargo fetch --locked
cargo test --locked --lib
cargo xtask build
cargo xtask check
cargo xtask test-e2e
```

開発・CIの基準はRust/Cargo 1.99.1です。PCセットアップ・ビルド・ライセンス生成・E2EもRustで実行するため、開発環境にもNode.js・pnpm・npmパッケージは不要です。`cargo xtask build`はホストOS向けのRust releaseビルドを`dist/`へ配置し、`cargo xtask licenses`はCargoの依存と`third-party/emoji-regex/`のライセンスから同梱文書を生成します。Windowsの正式実行物は`dist/plumivox.exe`、macOSは`dist/plumivox`です。利用者はネイティブ実行ファイルを直接使います。旧Nodeランチャーを指す登録の変更は[管理プロキシの移行手順](managed-proxy.md#旧タスクから切り替える)を参照してください。

`xtask build`とE2Eは、Cargoの`compiler-artifact`メッセージが返す実行ファイルを使います。`CARGO_TARGET_DIR`・`CARGO_BUILD_TARGET_DIR`・Cargo設定の`build.target-dir`による出力先を尊重し、既存の`target/debug`・`target/release`から推測して選びません。Windowsの配布ビルドはx64を保証するため、xtaskのMSVC／GNU／GNU LLVM環境に応じて`--target x86_64-pc-windows-msvc`／`--target x86_64-pc-windows-gnu`／`--target x86_64-pc-windows-gnullvm`を明示します。macOS ARM64もaarch64-apple-darwinを明示し、それ以外のビルドとE2Eは`CARGO_BUILD_TARGET`・`build.target`を尊重します。同じバイナリに複数の異なる実行ファイルが返る設定はエラーにします。E2Eのビルド対象は実行環境で起動できるターゲットにしてください。

macOSの正式配布物は、Apple Silicon Mac上でARM64ターゲットを導入して`cargo xtask build`を実行し、`lipo -archs dist/plumivox`で`arm64`単独を確認します。Windows x64ビルド、macOS ARM64ビルド、各OSの実動検証を別々に記録します。クロスビルドだけでKeychain・Unix socket・セットアップが動作したとは扱いません。

`cargo test --locked --lib`はRustのAPI境界・設定・セッション・プロキシテストを実行します。`cargo xtask test-e2e`は本体の単体テストとRustの各E2Eを実行し、対象OSのPCセットアップとVPS CLIも確認します。WindowsのDPAPI・ACL・ネイティブセットアップとmacOSのKeychain・Unix権限・セットアップを区別し、未実行・skipを成功へ数えません。

`cargo xtask test-setup-e2e`は検証用バイナリをビルドしてから、対象OSのネイティブPCセットアップE2Eを実行し、続いてVPSセットアップCLIを確認します。

全件検証には`tests/tls_e2e.rs`も含みます。RustのHTTPS偽APIと別プロセスのMCPを使い、検証CAでの成功、未信頼CAの拒否、ホスト名不一致の拒否を確認します。公開された合成証明書・鍵だけを使い、CA追加とHTTPSループバック許可は検証専用バイナリの明示モードに限定します。配布物の信頼設定や利用者の設定には追加しません。出力先は`PLUMIVOX_TLS_E2E_OUTPUT_DIR`または一時ディレクトリ配下`Codex/Plumivox/<UUID>`で、`summary.json`、`http-trace.json`、`diagnostics.json`を読みます。偽設定は呼び出し側で清掃します。TLSの交渉バージョンは`http-trace.json`の実測値で確認します。

macOSでは同コマンドが`test-fixture`付きのRustテストも実行し、鍵の初期作成ロックを保持した状態で既存セッションを並列復号できることを確認します。SSHなどでログインKeychainの操作が拒否される環境では、本人専用の一時領域に作った検証用Keychainを`PLUMIVOX_TEST_KEYCHAIN`へ指定できます。実Keychain APIを使い、既定Keychain・検索一覧を変更せず、本番実行ファイルはこの環境変数を参照しません。検証後は専用Keychainも清掃します。

E2Eは入力スキーマを拒否する標準MCPエラーと、アプリが返すJSONの業務エラーの両方を確認します。検証結果の `summary.json` と秘密を含まない `http-trace.json` は再現の証拠として保持できます。偽の設定・画像ファイルは検証後に清掃します。

E2E出力先は、本人が管理する信頼できる階層内に指定してください。Windowsでは新規出力先を本人限定の保護DACL付きで作成し、検証中は削除共有を許さないディレクトリハンドルを保持します。保持後にリンク・所有者・DACL・空であることを再確認してから書き込み、既存の親や出力先の権限は変更しません。通常のOS・本人用一時フォルダーの祖先は信頼する前提で、任意の指定先にある共有祖先すべてへの保護を保証するものではありません。

API系の失敗1件だけを再確認するときは、`PLUMIVOX_E2E_CASE`に`summary.json`のケース名を完全一致で指定して`cargo xtask test-api-e2e`を実行できます。一致するケースがなければ失敗します。既定の全体検証ではこの環境変数を未指定にし、個別再実行の成功を全件成功として扱いません。
