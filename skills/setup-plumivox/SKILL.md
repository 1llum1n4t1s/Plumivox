# Set up Plumivox

Read the bundled [setup guide](../../docs/setup.md) and continue from where the user currently is. On the PC, use `--setup` of `dist/plumivox.exe` on Windows or `dist/plumivox` on macOS (if the Windows Setup version is installed, `%LOCALAPPDATA%\PlumivoxApp\current\plumivox.exe`), and let the executable handle the interactive input. Use `setup/vps/` for the VPS assets. Do not depend on another repository, a development clone, or a particular user's storage location. Do not ask the user to install Node.js or Rust.

Reading and searching only need an API key and an X user name in the settings. Posting needs an authenticated public proxy and a session. To use the home line, build the path: the public proxy on the user's VPS → SSH reverse tunnel → the running Windows PC or Mac.

- Proceed in this order: `--setup --prepare-key` → transfer the public key and assets → `--check` and installation on the VPS → `--setup` on the PC → local `--setup --check` and the MCP `start_proxy`. When the user has to act, state concisely where, what to do, and which result to send back.
- Limit changes on the VPS to the targets and scope the user asked to build. Do not sign new contracts or make purchases. Do not resolve conflicts by deleting existing services, changing the firewall wholesale, or relaxing the administrator SSH settings.
- On x86_64 and aarch64 VPSs, prefer `setup/vps/plumivox-vps-setup-x86_64` and `plumivox-vps-setup-aarch64`. On other CPUs the bundled `install.sh` can be used as the Bash-compatible path. Use the scp route and CLI arguments from the setup guide, and do not switch to the Bash version to bypass the Rust version's safety checks.
- Create the transfer destination fresh under a remote home that only the user can write and that is not a link, with `umask 077; mkdir -m 700`. If it already exists, stop; do not delete or reuse it, and choose another unused name. Send the assets to an explicit `assets/vps/` and the public key directly into its parent, the new transfer destination, keeping every path consistent. If creating or transferring fails, do not continue. Before sudo, check the CPU, that the user owns and can write the location, that nothing is a link, and that the expected assets are in place. Do not run assets from a predictable shared `/tmp`.
- The public key, the Bash templates and the service definitions must be regular files owned by the sudo caller or root, not writable by third parties and not links, with their parent directories also under the user's or root's control. Keep the checks that use the fixed input contents, and do not edit or replace files during checking or installation. If a check stops on a root-owned ancestor of the destination, the sticky bit of a safe `/tmp`, or the safety of `/run` and the installation lock, do not weaken the protection or delete the lock; let the user check the environment.
- For new installations, both the Rust and Bash versions refuse, before making changes, any condition where ACLs, extended attributes, SELinux, `CAP_SYS_ADMIN` and the like cannot be handled safely. Keep this separate from the read-only check of an existing identical installation. `--check` performs no write probe, so even after it succeeds the installation may still stop safely, for example when `RENAME_EXCHANGE` is not supported within the same file system.
- New installations with the Bash version need GNU coreutils with `mv --exchange --no-copy -T` and `ln -T`, plus `getfacl`, `getfattr`, `sync`, `readlink` and `lsattr`. On environments with old coreutils or missing commands it stops before making changes; do not install or update anything automatically until the user has checked the environment.
- New installations also check for `CAP_SYS_ADMIN` in the initial user namespace, the mount IDs of the SSH configuration and its parent, and the absence of inode flags that cannot be preserved. Separate mounts, unverifiable states and conflicts with existing names are refused; do not work around them by reusing or overwriting existing data. If cleanup fails, do not bulk-delete or rerun until the user has checked the reported stage and backup locations and the exchange state.
- Avoid concurrent administrative operations while the SSH configuration is being exchanged. Both the Rust and Bash versions keep the old inode in a root-only backup directory; the user cleans it up after confirming that the old file descriptors are no longer in use, comparing the old and new contents, and checking that SSH administrative connections work. There is no automatic restore or cleanup. Do not treat a CLI check alone as a successful installation on the real system.
- Receive API keys, passwords and TOTP secrets through the wizard's secret prompts. Never ask for secret values in the conversation, MCP arguments, command arguments or logs. Only the `.pub` key goes to the VPS; the private key stays on the PC.
- The user confirms the SSH fingerprint through a trusted channel such as the VPS provider's console. Do not trust only the result of `ssh-keyscan`, and do not disable host key verification.
- When using the Windows Setup version, the user runs Setup to install it (the agent never runs or downloads Setup on their behalf). Setup registers Plumivox with Claude Code and Codex, so do not run `claude mcp add` or `codex mcp add` by hand. Do not use the Setup installation folder (`%LOCALAPPDATA%\PlumivoxApp`) as the storage location for settings or keys.
- After Setup registers Plumivox, an old plugin or a Toolport registration can start it through a second route. Setup only warns (in the guide shown when Plumivox is launched, in `app-update.log`, and as `legacyPlugins` in `app-update\setup-registration.json`); it never edits the user's Codex, Claude Code or Toolport settings. If the plugin is still enabled, tell the user to disable the plugin's MCP (add `[plugins."plumivox@plumivox-local".mcp_servers.plumivox]` with `enabled = false` to Codex's `config.toml`; in Claude Code use `/plugin`) or to remove the plugin, and to review any Toolport registration. Do not edit those files on their behalf.
- Get the plugin from the latest GitHub `main`. Use `installedPath` from `codex plugin add ... --json`, and do not guess the cache's version name. Do not add a registration line to `config.toml`.
- On both Windows and macOS, run the native `--setup` in a terminal, and never pass secret values as CLI arguments. Windows needs no PowerShell 7 and no execution policy change.
- The standard storage location is `%LOCALAPPDATA%\Kagayoi\Plumivox` on Windows and `~/Library/Application Support/Kagayoi/Plumivox` on macOS. Keep the selection order, including `PLUMIVOX_SECRETS_FILE` and an existing `~/dev/Secret/secrets.json`. The macOS session key is stored in the user's Keychain, and there is no fallback to plain text when the Keychain is unavailable.
- `--setup --check` checks only the local settings; `start_proxy` checks the PC egress and the SSH relay. Do not treat reachability of the public endpoint, a real login or a successful post as confirmed. For a setup-only request, do not log in or post; if the user asks for more, do it within that scope.
- The wizard and other CLI messages follow the user's language (`PLUMIVOX_LANGUAGE`, then the locale, then the OS display language). Reply to the user in the language of their request.

Check the storage location of existing settings and how to add accounts in [Configuration](../../docs/configuration.md), and starting, stopping and sharing of the relay in [Managed proxy](../../docs/managed-proxy.md). Do not turn explanations needed only for the first build into a checklist before every post.
